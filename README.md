# 파이썬 포트 스캐너 (Level 1 + Level 2)

MJsec 3주차(네트워크 기초) 과제 — nmap의 아주 쉬운 버전을 직접 구현한 것입니다.

> ⚠️ 본인 소유이거나 명시적으로 허가받은 호스트(127.0.0.1, 직접 띄운 서버, scanme.nmap.org)
> 에만 실행했습니다. 타인의 서버/회사망에는 절대 사용하지 마세요.

## 실행 방법

```bash
# 대화형 (host/port 입력 프롬프트)
python3 scanner.py

# Level 1: 순차 스캔
python3 scanner.py --host 127.0.0.1 --ports 1-100 --mode sequential

# Level 2: 스레드 스캔 (기본 모드) + 서비스 이름 추정
python3 scanner.py --host 127.0.0.1 --ports 1-1000

# 순차 vs 스레드 속도 비교
python3 scanner.py --host 127.0.0.1 --ports 1-1000 --compare
```

## 구현 과정

### Level 1 — 순차 스캐너
- `socket.socket(AF_INET, SOCK_STREAM)`로 TCP 소켓을 만들고 `connect_ex((host, port))`를
  호출해서 포트가 열려있는지 확인합니다. 반환값이 `0`이면 연결 성공(OPEN), 그 외(주로
  `errno 61 Connection refused`)면 CLOSED로 판단합니다.
- `sock.settimeout(1.0)`을 꼭 걸었습니다. 안 그러면 응답이 없는 포트(방화벽에 막혀 패킷이
  그냥 버려지는 경우)에서 OS 기본 타임아웃(수십 초)까지 기다리게 되어 스캔이 사실상 멈춥니다.
- `with socket.socket(...) as sock:` 구문으로 소켓을 쓰고 나서 자동으로 닫히게 했습니다.
  (포트 하나 확인할 때마다 소켓을 새로 만들고 닫는 구조 — 이게 바로 아래 체크포인트 질문의
  핵심입니다.)

### Level 2 — 멀티스레딩 + 서비스 추정 + CLI
1. **속도 개선**: `concurrent.futures.ThreadPoolExecutor`로 포트별 스캔 작업을 동시에
   제출(`submit`)하고 `as_completed`로 끝나는 대로 결과를 수거했습니다. 순차 버전과
   함수(`scan_port`)를 공유해서 코드 중복 없이 두 모드를 다 지원하게 만들었습니다.
2. **서비스 이름 매핑**: 1차로 `socket.getservbyport(port)`(시스템의 `/etc/services`
   참조)를 쓰고, 여기서 못 찾으면(`OSError`) 흔한 포트들을 직접 적어둔 `COMMON_SERVICES`
   딕셔너리로 보완했습니다.
3. **CLI 인자 처리**: `argparse`로 `--host`, `--ports`, `--threads`, `--timeout`, `--mode`,
   `--compare`를 받습니다. 인자를 안 주면 Level 1 방식대로 `input()`으로 물어보게 해서 두
   레벨의 요구사항을 한 파일에서 다 충족하도록 했습니다.

### 속도 측정 결과 (127.0.0.1, 1-1000번 포트, 스레드 50개)

```
[Sequential] Scanning ports 1-1000...
Sequential scan finished in 0.03s (open: 0)

[Threaded] Scanning ports 1-1000 with 50 threads...
Threaded scan finished in 0.04s (open: 0)

=> Speedup: 0.8x faster with threads
```

예상과 다르게 로컬호스트에서는 스레드 버전이 더 빠르지 않았습니다(오히려 스레드 생성/스케줄링
오버헤드 때문에 살짝 느림). 이유를 찾아보니, **닫힌 포트에 대한 응답 속도** 때문이었습니다.
`127.0.0.1`에 닫힌 포트로 연결을 시도하면 커널이 즉시 `RST`를 돌려주기 때문에 각 연결 시도가
이미 매우 빠르게(거의 0초) 끝납니다. 즉 순차 스캔이어도 1000개 포트를 거의 지연 없이 다
훑을 수 있는 것입니다. 반대로 **원격 호스트**를 스캔하거나 방화벽이 패킷을 그냥 drop하는
환경(응답이 없어서 타임아웃까지 기다려야 하는 상황)에서는 포트 하나당 최대 1초씩 걸리므로,
1000개를 순차로 돌리면 이론상 최대 1000초가 걸리는 반면 스레드 50개로 돌리면 이론상 약
20초(1000/50)로 줄어듭니다. 즉 스레딩의 효과는 "닫힌 포트의 응답이 느린 환경"에서 극적으로
드러난다는 것을 실험을 통해 체감했습니다.

## 체크포인트 질문 답변

**Q1. 이 스캐너가 포트 하나를 확인할 때, 3-Way Handshake의 어느 단계까지 실제로 일어나는
걸까요?**

포트가 **열려 있는 경우**에는 3-Way Handshake가 전부(SYN → SYN/ACK → ACK) 일어납니다.
`connect_ex`는 운영체제의 TCP 스택에게 "연결해줘"라고 요청만 하는 함수이고, 실제 SYN 패킷
전송/SYN-ACK 수신/ACK 전송은 커널이 처리합니다. 핸드셰이크가 완료되면 `connect_ex`가 `0`을
반환하고, 우리는 바로 `with` 블록을 빠져나가면서 소켓을 닫습니다. 이때 아직 아무 데이터도
주고받지 않았으므로 애플리케이션 레벨(HTTP 요청 등)까지는 가지 않고, 소켓을 닫을 때 FIN(또는
연결 유지 여유 없이 바로 닫으면 RST)을 보내서 연결을 끊습니다. 즉 이 스캐너는 전형적인 **TCP
Connect Scan (nmap의 `-sT` 방식)**이고, SYN만 보내고 ACK는 보내지 않는 **SYN Scan (`-sS`,
"half-open scan")**과 달리 핸드셰이크를 끝까지 완료한다는 점이 다릅니다.

포트가 **닫혀 있는 경우**에는 핸드셰이크가 아예 1단계에서 끝납니다. 우리가 SYN을 보내면
대상이 "이 포트는 리스닝 중이 아니다"라며 바로 **RST**를 돌려보내기 때문에, SYN/ACK 단계로
넘어가지 못하고 연결이 즉시 거부됩니다(`connect_ex`가 0이 아닌 에러 코드, 보통
`ECONNREFUSED`를 반환).

**Q2. connect_ex와 connect의 차이는 무엇이고 왜 스캐너에는 connect_ex가 더 적합할까요?**

`connect()`는 연결에 실패하면 **예외(OSError)를 발생**시킵니다. 그래서 그냥 `connect()`를
쓰면 포트가 닫혀 있을 때마다 `try/except`로 예외를 잡아줘야 하고, 포트 하나하나를 "정상 흐름"이
아니라 "예외 처리"로 다뤄야 해서 코드가 지저분해지고(모든 포트가 닫혀있는 게 디폴트인
스캐너 입장에서는 예외가 거의 항상 발생) 예외 객체 생성 비용도 추가로 듭니다.

`connect_ex()`는 예외를 던지는 대신 **정수 에러 코드를 반환**합니다(성공 시 `0`, 실패 시
`errno` 값, 예: `ECONNREFUSED`). 그래서 `if result == 0:` 같은 단순한 조건문으로 OPEN/CLOSED를
판별할 수 있고, try/except 없이 수백~수천 개의 포트를 반복문(또는 스레드)으로 깔끔하게 돌릴 수
있습니다. 포트 스캐너처럼 "실패(닫힘)가 예외적인 상황이 아니라 오히려 더 흔하게 나오는 정상
결과값"인 경우에는, 실패를 예외가 아니라 반환값으로 다루는 `connect_ex`가 훨씬 적합합니다.

**Q3. 스레드를 너무 많이 띄우면 어떤 문제가 생길 수 있을까요?**

- **파일 디스크립터(FD) 제한**: 소켓도 운영체제 입장에서는 파일 디스크립터 하나입니다. 리눅스/
  macOS는 프로세스당 열 수 있는 FD 개수에 기본 제한(흔히 `ulimit -n` 256~1024)이 있는데,
  수천 개의 소켓을 동시에 열려고 하면 `OSError: [Errno 24] Too many open files`가 발생해서
  스캔 자체가 실패할 수 있습니다.
- **스레드 생성/컨텍스트 스위칭 오버헤드**: 스레드 1000개를 한 번에 띄우면 OS 스케줄러가
  그만큼 많은 컨텍스트 스위칭을 해야 해서, 오히려 스레드 개수를 적당히(예: 50~100개) 유지하는
  것보다 느려지거나 메모리를 더 많이 쓸 수 있습니다. (GIL 때문에 파이썬 스레드는 CPU 연산을
  병렬로 못 돌리지만, 이 스캐너처럼 대부분 "소켓 연결 대기(I/O)"인 작업은 I/O 중에 GIL이
  풀리므로 스레딩 효과를 볼 수 있습니다 — 다만 그 이점도 스레드 수가 무한정 늘어난다고
  무한정 커지지는 않습니다.)
- **대상 서버의 방어 로직(트리거 가능성)**: 아주 짧은 시간에 한 호스트로 수백~수천 개의 SYN이
  몰리면 침입 탐지 시스템(IDS/IPS)이나 방화벽의 **포트 스캔 탐지 룰**(예: fail2ban, SYN flood
  방어)에 걸려서 내 IP가 일시적으로 차단(block/rate-limit)될 수 있습니다. 심하면 이런 트래픽
  패턴 자체가 (허가 없이 할 경우) DoS 공격처럼 보일 수도 있습니다. 그래서 실전 도구인 nmap도
  `-T` 옵션으로 스캔 속도(타이밍 템플릿)를 조절할 수 있게 해줍니다.

## 느낀 점 / 데이터·보안 자동화 관점에서의 연결고리

이번 과제를 하면서 느낀 건, 포트 스캐너가 사실 **"조건에 맞는 호스트/포트를 찾아서 분류하고
집계하는 작은 데이터 파이프라인"**과 구조가 똑같다는 점이었습니다. `scan_port()`가 원자적인
작업 단위(row 하나를 처리하는 함수)이고, `ThreadPoolExecutor`로 그 작업을 병렬로 뿌린 뒤
`as_completed`로 결과를 모아 집계(open/closed 카운트)하는 흐름은, 데이터 엔지니어링에서
API를 수백 번 호출해 데이터를 수집하거나 여러 서버의 로그를 동시에 가져오는 작업과 패턴이
거의 같습니다. 나중에 보안 자동화(예: 사내 자산의 열린 포트를 주기적으로 스캔해서 변화가
생기면 알림을 보내는 스크립트)나, 데이터 수집 자동화(여러 엔드포인트를 동시에 호출해 결과를
테이블로 적재하는 배치 잡) 쪽으로 이 구조를 그대로 확장할 수 있겠다는 생각이 들었습니다.
